# Contributing

Small, focused pull requests are easiest to review. Bug fixes, accessibility, docs and theme tokens are always welcome; for a new component or any breaking change to the public API, open an issue first so we agree on the shape before you write it.

## Get set up

```bash
git clone https://github.com/dan-netrunner/night-city-ui.git
cd night-city-ui
npm install
npm run dev   # http://localhost:5173
```

`main` is the only long-lived branch and it is protected: changes arrive as a pull request with green CI, reviewed by the maintainer. `gh-pages` is generated by CI — never branch from it or push to it.

## Where things live

| Path | What belongs there |
| --- | --- |
| `src/components/*.tsx` | One file per component group (`Button`, `Fields`, `Display`, …) |
| `src/components/index.ts` | Barrel: every public component is re-exported here |
| `src/index.ts` | Package entry: styles + public API. Nothing demo-only goes here |
| `src/theme.tsx` | `ThemeProvider`, `useTheme`, the `THEMES` metadata list |
| `src/styles/tokens.css` | Design tokens and the four `[data-theme="…"]` blocks |
| `src/styles/ui.css` | Component styles (`.cp-*`) |
| `src/styles/app.css` | Docs site layout only — never needed by consumers |
| `src/pages/*` | Demo/documentation pages |
| `GUIA_DE_USO.md` | Spanish guide |
| `.github/workflows/` | Pages deploy and npm publish |

## Rules of the kit

- **Structure in `ui.css`, values in `tokens.css`.** A skin must switch with `data-theme` alone, without touching markup. A hard-coded color is acceptable only inside an `@scope ([data-theme="…"])` block, when that skin genuinely needs an exception.
- **Naming:** classes are prefixed `cp-`. A new component means one file in `src/components/`, an export in `src/components/index.ts` (it reaches the package through `src/index.ts`), and its props type exported.
- **Native elements first** — `<button>`, `<input>`, `<details>`, `<dialog>` — then ARIA only where the platform can't express the semantics. Keep the visible focus ring, honor `prefers-reduced-motion`, and mark decorative texture `aria-hidden`. If you touch interaction, test it keyboard-only.
- **No new runtime dependencies** beyond React. No fonts, textures, icons or other assets shipped from the game; names and inspiration are fine.
- **Install scripts are allow-listed.** npm blocks dependency lifecycle scripts unless the package appears in `allowScripts` in `package.json` (today: `esbuild@0.28.2`). If a dev dependency legitimately needs one, run `npm install-scripts approve <name>@<version>` and commit the entry, so the review is visible in the diff. Dependabot opens at most a few grouped PRs a week; majors for `vite`/`typescript` are deliberate and stay out of that.
- **Show it in the docs.** Add the component to the relevant page (`src/pages/ComponentsPage.tsx`, the Playground, or the Guide) so it is documented the day it lands. If theming behavior changes, update the Guide page and `GUIA_DE_USO.md` in the same PR.

## Checks before you open a PR

```bash
npm test              # vitest suite for the kit
npm run test:coverage # the same suite plus the coverage thresholds CI enforces
npm run build         # tsc --noEmit + docs build — this is what CI runs
npm run build:lib     # package build: ESM bundle + style.css + .d.ts
```

CI runs all three on every pull request, plus `npm audit --omit=dev` and a check that the tarball contains only library output. New components need a test: render it, assert the accessible role or label, and assert the thing that breaks if the markup drifts.

Both write to `dist/`, the last one to run wins; `package.json` `files` allow-lists the library output only, so docs chunks can never ride along, and `prepublishOnly` rebuilds the package before any publish.

Look at your change under all four skins using the theme switch in the header; a component that only works in the default one is not done.

## Testing

The supported environment is Vitest with the `jsdom` environment, configured in [`vitest.config.ts`](./vitest.config.ts). CI runs the suite on Node 22 ([`ci.yml`](./.github/workflows/ci.yml)); the publish job runs it on Node 24 ([`publish-npm.yml`](./.github/workflows/publish-npm.yml)). You run it with `npm test`; CI runs it automatically on every pull request, and the publish workflow runs it again before every release.

34 tests cover the kit today. [`src/components/kit.test.tsx`](./src/components/kit.test.tsx) renders the components and asserts their accessible roles, labels and ARIA wiring — buttons and fields, tabs keyboard behaviour, modal and toasts, the code-copy — and [`src/theme.test.tsx`](./src/theme.test.tsx) drives `ThemeProvider` through skin switching, the `theme-color` meta and `nc-theme` persistence, including a storage backend that throws. A property-based fast-check test ([`progress.property.test.tsx`](./src/components/progress.property.test.tsx)) pins the `Progress` clamp and aria values for arbitrary inputs.

Policy: any behavioural change must add or update a test in the same pull request, and every new component needs at least one test asserting its accessible role or label. A red suite blocks the PR — the required `build` check (the CI job) runs the suite among its steps.

### Coverage

`npm run test:coverage` instruments the **shipped surface only** (`src/components/*.tsx` and `src/theme.tsx`; the docs-site pages and the demo `ComponentWorkbench` are excluded because they are not what the package exports). The thresholds live in [`vitest.config.ts`](./vitest.config.ts) — 90% statements, 80% branches, 85% functions, 90% lines — and CI enforces them with `set -o pipefail`, so `tee` cannot mask a threshold failure. The measured numbers are posted to the run's job summary.

## Commits and pull requests

- Conventional prefixes, matching the existing history: `feat:`, `fix:`, `docs:`, `ci:`, `chore:`.
- Code, demo usage and docs belong in the same change.
- Commit with an email you control on GitHub (`git config user.email …`) — the commit author is the attribution you get.
- In the PR description say what changed and why, and attach a screenshot for anything visual.

## Releases

Maintainers only. `npm version patch|minor|major`, merge to `main`, and GitHub Actions publishes to npm with provenance through OIDC trusted publishing and deploys the docs site to `gh-pages`. Pushing the version tag also opens the matching GitHub Release with the tarball attached. Contributors never need npm credentials or tokens.

Every user-visible change gets a line in [CHANGELOG.md](./CHANGELOG.md) under *Unreleased*; the release commit moves it under the version heading.

## Permissions

There is no path to write access except reviewed pull requests: [`CODEOWNERS`](./.github/CODEOWNERS) routes every file to the maintainer, and `main` requires two approving reviews, the required status checks (`build` and both CodeQL analyses) and an up-to-date branch. Repository access is never granted automatically; collaborator permissions are assigned manually, at the lowest level that still does the job. Release authority — npm, the GitHub environments, secrets — stays with the maintainer.

## Keeping the badge honest

[`.bestpractices.json`](./.bestpractices.json) holds the proposed answers for this project's
[OpenSSF Best Practices badge](https://www.bestpractices.dev/projects/16895) entry. The badge
system reads it to prefill the form; a maintainer still reviews and saves each answer, and an
`Unmet` or `N/A` is allowed and expected where it is true.

The file also carries the answers for the badge's own classic criteria. To write them into the
entry without clicking through every section, use the local helper, which pins the badge
project's modifier module by commit and checksum and authenticates with your 48-hour session
cookie:

```bash
./scripts/bestpractices-sync.py --dry-run          # what would be sent
./scripts/bestpractices-sync.py                    # asks for _BadgeApp_session
```

The session cookie is your live credential: export it in your shell, never commit it, never put
it in a CI secret, and log out of bestpractices.dev when done to invalidate it.

When a change adds, removes or alters a control — a CI gate, a workflow permission, the release
process, a policy in `SECURITY.md` — update the matching `OSPS-*_status` and its `_justification`
in the same pull request. Never mark something `Met` that cannot be pointed at in this repository.
